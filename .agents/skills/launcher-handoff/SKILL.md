# 別PCへの引継ぎ確認

コピーされたプロジェクトで、展示運用・ソース修正・配布物のビルドのうち、利用者が必要とする作業をできる状態にする。コピーだけで環境が再現したと判断しない。

## 引継ぎの目的を確認する

- 対象プロジェクトの [AGENTS.md](../../../AGENTS.md) を読む。以下のパスはそのプロジェクトルートを基準にし、コピー元PCの絶対パスを手順へ固定しない。
- 「展示アプリを使いたい」「コードを直したい」「配布用アプリも作りたい」を区別する。依頼から分かる場合は質問せず、目的に必要な確認だけを行う。
- コピー先が現在接続している環境かを確認する。未接続PCについては確認手順を提示し、実施済みと扱わない。
- 環境確認の依頼と、依存関係の再構築・設定変更・実データ更新を区別する。環境構築まで依頼されていれば必要な準備を進め、既に許可された操作を再確認しない。

## コピーされた内容と配置を調べる

Git追跡一覧ではなく実フォルダを確認する。`.gitignore` で除外された設定、素材、作品、バックアップ、運用資料も引継ぎ対象に含まれる。

| 目的 | 主な確認対象 |
| --- | --- |
| 展示運用 | `launcher-win/`、配布EXE、`resources/config.json5`、表示資源、作品データ、バックアップ |
| 作品生成・更新 | `exhibition-automation/` の設定と使用するスクリプト／EXE、入力CSV・提出作品・サムネイルのDriveミラー、ステージング・本番・バックアップの配置 |
| ソース修正 | `exhibition-launcher/` と `exhibition-automation/` のソース、依存関係定義、テスト、設定・素材・運用資料 |
| ビルド | 各 `build.ps1` が要求する環境、Node.js/npm、Python・PyInstaller、素材、パッケージ対象と出力先 |

- `path_utils.py` の配置制約を確認する。現在は `C:/Users/<ユーザー名>/...` を要求し、`{user_name}` はスクリプト／EXEの配置パスから抽出する。ログインユーザー名や任意のドライブへ自動追従するとは説明しない。
- ソース側の2つの `config.json5` と配布版の `resources/config.json5` を分ける。相対パスの基準、CSV入力、ミラー内の作品・サムネイル、ステージング、本番、バックアップの実パスを確認する。
- Driveミラーの読込は継続する。同期・アカウント状態をファイルの存在だけから断定せず、必要なファイルの読込可否を確認する。生成済みworksのDrive往復コピーは通常経路にしない。
- 欠けている設定・作品・素材を仮データで置き換えない。必要なものと、その入手・配置が未確認であることを示す。

## 目的に必要な開発環境を整える

- コピーされた `node_modules/` と `.venv/` を動作保証された環境として扱わない。実行ファイルの有無だけでなく、使用するインタープリタ・依存関係を確認する。`.venv/pyvenv.cfg` のコピー元Pythonパスも調べる。
- Electronの依存関係は `package.json` と `package-lock.json`、Pythonは `requirements.txt` を確認する。Node.js・Pythonの対応範囲を、コピー元のバージョンだけで決めない。
- Pythonのビルドは `build.ps1` が `.venv/Scripts/pyinstaller.exe` を使う。テストのpytestは現在 `requirements.txt` に含まれないため、インストール済みと仮定しない。
- 環境再構築が必要なら、対象・手順・書換範囲を明示して依頼の範囲で行う。旧環境や実データを一括削除せず、AGENTS.mdのデータ保護方針を守る。

## 確認結果を分けて伝える

- 展示運用、ソース修正、ビルドについて、確認できたことと未確認のことを分けて報告する。起動できただけで「開発環境の引継ぎ完了」としない。
- 必要な起動・テスト・ビルドのコマンドは現在の `package.json`、`build.ps1`、テスト構成から選ぶ。設定確認だけのために作品生成・本番反映・配布更新を実行しない。
- 未接続PCでの操作案には、どのPCのどのフォルダで何を行い、どの結果を確認するかを添える。
- 完了時は、目的に対する確認状況、変更した環境・設定、不足ファイル、次の具体的な作業を伝える。該当する運用資料も案内する。
